# PML shortcomings → TSPML improvements

> The "why TSPML" document. Each row is a concrete weakness of PolyModLoader (verified against `src/PolyModLoader.ts` tag `0.6.1`) mapped to a specific TSPML fix. An adversarial audit reviewed this list for accuracy; its corrections are incorporated below (notably the physics-coverage fix and several added weaknesses).

## Summary table

| # | PML weakness | Why it hurts | TSPML improvement |
|---|---|---|---|
| 1 | **Redistributes the whole copyrighted game** (`main.bundle.js` ~3.4 MB + WASM + chunks + assets) inside the repo/releases; statically prepends its bootstrap to `main.bundle.js`. | Legally fraught; forces re-shipping the entire game on every Kodub update; bloats every release. | Ships **only** loader + mappings metadata; fetches the user's own **live** game and transforms it in place. No bundle in the repo. |
| 2 | **Mixin engine = `toString()` + `indexOf(token)` + `eval()`** (`PolyModLoader.ts:1994-2130`). Tokens are exact-string literals. | One whitespace/paren change → `indexOf` returns -1 → throws "Token not found" and the **entire loader fails to boot**. Short/ambiguous tokens (`);`) silently patch the wrong site. | Stable names → concrete locators via the **mappings file** + **AST** transforms (structural, not substring). Failures are per-hook and specific; never a boot-abort, never a silent mis-target. |
| 3 | **Hardcoded mangled identifiers** (`enum Variables`: `uf`, `P.A`, `ge.A`, `no`; plus `R.gn`, `R.GG`, `i.l`, `cc.prototype`, `ei.prototype`). | Survive only until the game is re-bundled; PML is effectively **frozen to one build** (`v0.6.1-0`) and every mod breaks each release until re-derived by hand. | Versioned mappings map stable names to the *current* build's mangled refs; a webcrack/wakaru pipeline regenerates the map. Only the map + bridge are version-coupled. |
| 4 | **Only 4 lifecycle hooks** (`preInit/init/postInit/onGameLoad`); no first-class render/physics/track/input/UI/network hooks. | Every real behavior change requires injecting into minified functions (the most fragile path). | Rich event bus + registries (physics/render/track/input/checkpoint/UI/network) wired by a loader-owned bridge; most mods never touch internals. |
| 5 | **`getSetting()` always returns a string** regardless of `SettingType`. | Every mod hand-parses booleans/numbers — needless repeated footgun. | `api.settings.getSetting` returns **typed** values; `@tspml/api` `.d.ts` enforces this at compile time. |
| 6 | **No automatic dependency resolution** — semver ranges but no topo-sort, cycle detection, or conflict resolution; load order is purely manual `reorderMod`. | Inter-mod deps rest on a weak contract; users hand-order mods ("biggest-change higher"); silent breakage from version conflicts. | Auto topological sort + cycle detection + **explicit** incompatible-version conflict errors. User priority hints layer on top, not replace resolution. |
| 7 | **Zero sandboxing** — mods are full-trust ES modules with DOM/fetch/storage access **plus an `eval(path)` bridge** into the whole game module graph (incl. multiplayer netcode). No CSP. | A malicious mod can hijack sessions, exfiltrate data, or piggyback on the spoofed Origin. No permission/isolation/signing. | Capability declarations are **consented-advisory** (load-time prompt); raw `window`/`eval` requires an explicit "unsafe" consent. *(Honest scope: same-realm JS cannot truly enforce isolation without SES/membrane — see [safety-and-fairness.md](../design/safety-and-fairness.md).)* |
| 8 | **Fairness is advisory only** — `touchingPhysics`/`isVanillaCompatible()` feed `isModsVanillaCompatible` into invite **metadata** (not enforcement), via the *most brittle* mixin form (`REPLACEBETWEEN` with `tokenStart===tokenEnd`). Server replay validation is still "in development." | A physics/speed mod is trivially a leaderboard cheat; the only signal is metadata a mod can lie about → ban risk. | **Warn-only** vanillaSafe classification + prominent risk labels + a determinism lint; docs disclose ban risk honestly. (TSPML is warn-only by the project's locked decision; the determinism lint helps mods not *accidentally* break replays.) |
| 9 | **Thin DX** — types ship but only via a version-pinned CDN URL (no npm/tsconfig path); no scaffold, dev server, HMR, or template; every change forces a full reload; desktop doesn't auto-update. | Slow, error-prone authoring; high onboarding friction. | `npx create-tspml-mod`, npm `@tspml/api` types, a Vite dev harness with **scoped** HMR, a VS Code extension, versioned docs. |
| 10 | **Stale docs** — wiki admits "under construction…outdated"; documents `simInit`/`registerSimWorkerClassMixin` that **don't exist** in 0.6.1; README is two sentences with no install steps; pre/post-0.6.0 manifest split is confusing. | Modders code against removed/non-existent APIs and hit silent failures; users can't install from the README. | Docs-first: a versioned docs site generated partly from type defs (can't drift), covering install, quick-start, full API reference, mixin guide, mappings, publishing, troubleshooting. |
| 11 | **Three distribution surfaces** (web `pages`-branch, Electron per-OS zips, separate `PML-Mobile`) re-released in lockstep per game version; desktop **doesn't auto-update**. | Desktop users stuck on stale versions; maintainers shoulder a 3-way release burden; the web version needs a Discord-only side-mod (`PolyProxy`) for online play. | One loader core driving a portal + extension + userscript, all auto-updating; secondary paths for resilience. |
| 12 | **Synchronous XHR on the main thread** — not just `applyChunkMixin`, but also `getPhysicsLibURL`, wasm loading, and `getSimURL`. | Main-thread jank + a latency/failure cliff for every chunk/worker/physics mixin. | Async fetch+transform pipeline with results cached in IndexedDB by bundle hash; no synchronous main-thread network. |
| 13 | **No unload/cleanup hook**; error UX is `alert()` (21 call sites). | Mods that grabbed resources/listeners leak; failures are un-diagnosable popups with no compatibility context. | `loader.onUnload` for documented cleanup + a structured compatibility report listing, per mod, what resolved/failed. |
| 14 | **Top-level network dependency** — `const pmlversion = await fetch('https://codeberg.org/.../tags')` at module top level. | The loader's own version identity depends on a third-party host being up; silently degrades to "untagged" and mis-behaves if Codeberg is slow/down. | Offline-first: installed mods + the current map work with zero network; network only for discovery/publish/map updates. |
| 15 | **No test framework at all** — `npm test` just launches Electron+devtools. | Zero automated coverage of the mixin engine, dependency resolver, or version gating (silent-breakage hotspots). | TypeScript + a real test runner from day one (loader core unit tests in M1); regression coverage for resolution + conflict logic. |
| 16 | **Poor repo hygiene** — compiled JS/`.d.ts` auto-committed by a CI bot (can drift from `src/`); a ~3 MB stray dev artifact (`Untitled-1.js`) is checked in. | Contributors must trust bot commits; output drifts from source; repo is bloated/confusing. | Clean monorepo, build artifacts gitignored, source-of-truth in `src/`, reproducible local builds, no bot commits. |

## Audit corrections (important)

- **Physics coverage (material inaccuracy, fixed):** earlier notes claimed PML's "sim-worker mixins are unimplemented post-0.6.0" and "physics mods are blocked." **This is wrong against the 0.6.1 source.** `registerSimWorkerMixin` **is** implemented, and `getSimURL()` fetches `simulation_worker.bundle.js`, string-splices it, and spawns the worker from a Blob URL (same for the physics lib + wasm). So **PML can reach physics.** TSPML's advantage on the physics axis is therefore **better DX + determinism-quarantine + a stable event surface** — *not* "enabling physics mods that PML couldn't do." (TSPML's physics events also execute *inside* the worker to preserve determinism, which is a genuine architectural improvement over PML's approach.)
- **Sync XHR broadened:** the blocking-fetch problem is broader than `applyChunkMixin` — it also affects `getPhysicsLibURL`, wasm loading, and `getSimURL`.
- **Eval bridge severity:** `getFromPolyTrack`/`getFromPolyTrackGlobal` is literally `(path) => eval(path)` — an **arbitrary eval sink** into the entire game module graph, not merely "a bridge." (Row 7.)
- **"Breaks every release" is severe but not always total:** some global/string-anchored mixins and worker-protocol-string hooks do survive a release. Breakage is pervasive, not 100%.
- **Strategic adoption risk:** the same `polytrackmods` org maintains **`pml2`**, an explicitly next-gen loader. The incumbent may self-disrupt and narrow the window TSPML assumes is open — name this as a positioning risk.

## Net

The shortcomings list is well-grounded in the source. TSPML's value proposition is **not** "PML can't do X" — it is: **(a) a stable, mappings-backed API so mods survive updates** (PML's single biggest pain), **(b) far better DX** (types, scaffold, scoped HMR, real tests), **(c) honest, diagnostic failure modes** (no boot-aborts, no silent mis-targets), and **(d) a cleaner legal/online posture** (no game redistribution). Physics is a DX+architecture win, not a capability PML lacks.
